# Структура Базы Данных

Значит сегодня поговорим про структуру базы данных. Мы не говорим про саму программу, про её интерфейс — просто расскажу, из чего состоит база данных, основные функциональные элементы (уровень идей). Работаем с базой данных Oracle, используем программу Toad для просмотра и редактирования объектов.

Важно: при операциях импорта/экспорта выполнять их от имени Sys или System с правами SysDBA — в противном случае можно выгрузить не все данные (если экспорт делать от владельца данных).

Схемы

* На сервере может храниться сразу несколько схем (данных разных предприятий).
* Обязательные единичные схемы на сервере: UN4PUBLIC, UN4PACK, UN4$REPOZITAR — каждая присутствует в единственном экземпляре.
  * UN4PUBLIC хранит общие алгоритмы, вынесенные в отдельную схему.
  * UN4PACK — ранее использовался для сжатия/передачи дизайнов (сегодня редко актуально).
  * UN4$REPOZITAR — набор общих справочников региона (список предприятий, экономических агентов и т.п.); предназначен для обновляемой распространённой схемы.

Традиционно схема с данными предприятия называется UN4, но на одном сервере схемы могут называться по имени клиента (например TUTUN, MTC и т.д.). Удобно, если имя схемы совпадает между офисной копией и клиентом — это облегчает импорт/экспорт.

Общие принципы:

* Обычно пароли на схемы совпадают с именем схемы.
* Для работы с таблицами и объектами используйте вьюшки, а не прямые обращения к таблицам — это даёт уровень абстракции и гибкости.

Оперативные данные (Ключевые таблицы, документы и проводки)

Таблица TMDB\_DOCS

* Ключевая таблица оперативного учёта: одна запись = один документ.
* Основные поля:
  * COD — первичный ключ (в других таблицах может называться NRDOC).
  * DATAMANUAL — дата проведения документа (вводит операционист).
  * SYSFID — число, определяющее тип документа (влияет на алгоритмы обработки).
  * USERID — заполняется триггером (кто сохранил документ).
  * NRMANUAL — ручной номер из бумажного документа (для удобства поиска).
  * DOCCOLOR — рассчитывает цвет документа (нормальный, без проводок, аннулирован и т.п.).
  * F, M, DIV — поля управления видимостью/фильтрами (POLICY). DIV — например, филиалы.
* Важное правило: при смене SYSFID документ начинает обрабатываться другим программным куском — операция мощная и может привести к ошибкам, но в ряде случаев полезна.

Таблица TMDB\_CM (проводки, Carte Mare)

* Таблица проводок со сложной структурой аналитики.
* Первичный ключ: NRDOC (номер документа), COD (код проводки), SPTYPE.
  * SPTYPE: 0 — обычная проводка; 1 — парная (для ускорения расчёта сальдо, зеркальная проводка с минусом); 2 — зарегистрированное сальдо.
* Поля и назначение (обзор):
  * FUNCT — группа проводок в документе (например: движение материалов, НДС, скидки) для селективных перерасчётов.
  * ISVALID — NULL (валидна) или не NULL (дезактивирована и не учитывается).
  * CODFCDEBAZA / CODREF — код базовой проводки (связь проводок, напр. НДС → конкретной приходной проводке).
  * NRDOCFCDEBAZA — номер документа базовой проводки (редко используется с другой сущностью).
  * Аналитика дебет/кредит:
    * DT, CT — основные аналитические поля (счёт из плана счетов).
    * DT1/CT1 — дополнительный субсчет (используется для дополнительной разбивки, например виды скидок).
    * DTSC, DTDEP, DTSC1 (и аналогично CTSC, CTDEP, CTSC1) — ссылки на TMS\_UNIVERS (универсальный справочник аналитики: сотрудники, контрагенты, материалы, ОС и т.д.).
    * DTNRDOC/CTNRDOC — ссылка на другой документ/контракт (числовая).
    * DTSTRSC/CTSTRSC — строковая аналитика (сохранение ведущих нулей, серии и т.п.).
    * DTNRCM/CTNRCM — участвуют в фильтрации видимости (аналог DIV).
    * DTDATA/CTDATA — аналитика типа DATE (например: месяц начисления ЗП).
  * Многосуммовой учёт:
    * SUMA — обычная сумма.
    * SUMAVALDT, SUMAVALCT — суммы в валюте (отдельно для дебета и кредита) + VALUTADT/VALUTACT.
    * SUMAGAAP — дополнительное суммовое поле (универсальное запасное поле).
  * Количества:
    * CANT — стандартное количество.
    * CANT1 — альтернативное количество (может различаться по дебету/кредиту).
  * DTDIV, CTDIV — подразделения/филиалы по дебету/кредиту (внутренние перемещения).
* SPTYPE=1 — парная проводка: при генерации каждой основной проводки создаётся зеркальная запись (специально для ускорения расчёта сальдо). Триггер, который это делает, критичен: его поломка вызовет несоответствия между оборотами и сальдо.
* SPTYPE=2 — зарегистрированное сальдо: используется для фиксации сальдо на дату (оптимизация при большом объёме движений). Часто все сальдо регистрируются на конец периода; такие записи имеют особую временную метку, чтобы не попадать в обычные периоды.

Связанные регистры/таблицы для документов

* TMDB\_DOCS\_ADD — доп. системные атрибуты документа (например, кто создал документ).
* TMDB\_DOCS\_LOG — журнал истории документа (лог действий: START EDIT, CANCEL EDIT, генерация проводок и т.п.). Эта таблица намеренно не имеет FK на TMDB\_DOCS (чтобы история сохранялась даже после удаления документа).
* При построении зависимых таблиц (many-to-one) принято включать в ссылающуюся таблицу полный набор полей первичного ключа родителя + дополнительное поле для расширения (это упрощает выборки и хранение связей).
  * При этом важно указывать ON DELETE CASCADE в FK и DEFERRABLE INITIALLY DEFERRED (чтобы проверки делались на COMMIT).

TMDB\_CST3A / TMDB\_CST3B / TMDB\_CST3C (спецрегистры, кастомизируемые)

* CST = Customizable; таблицы-абстракции для хранения произвольного набора полей, удобного для конкретного документа.
* TMDB\_CST3A: PK = NRDOC + NRDOC1 (позволяет хранить несколько строк на документ для NRDOC1).
* TMDB\_CST3B: PK = NRDOC + NRDOC1 + NRDOC2 (подчинена CST3A).
* TMDB\_CST3C: аналогично — далее уровень вложенности.
* Принцип: включать PK родителя в PK дочерней таблицы упрощает выборки и поддерживает простую семантику Master-Detail.
* При создании FK в ссылаемой таблице нужно создать неуникальный индекс по набору полей, соответствующему FK — это предотвращает блокировку всей таблицы при Select FOR UPDATE и уменьшает вероятность deadlock'ов.

Примеры имён и конвенций

* Y\* — таблицы/объекты для специфических нужд конкретного клиента (префикс Y + аббревиатура клиента). Используются для локальных расширений, не распространяемых на все схемы.
* ZTEMP / ZZTEMP — временные таблицы:
  * ZTEMP — мусорные/временные, которые можно удалять.
  * ZZTEMP — глобальные временные таблицы, структура которых постоянно существует; их удаление нарушит алгоритмы.

Универсальные документы и регистры

* 201M (шапка) / 201D (табличная часть) — старая попытка универсального документа (шаблонный документ с настраиваемыми полями).
* CST1 — документ с 2 гридами.
* CST2 — CST1 + настраиваемая шапка (201-подобная).
* CST3 — документ с 3 гридами + настраиваемая панель (DG1P21). Самый гибкий: 3 грида, настраиваемая шапка, панели справа/снизу, возможность включать/выключать грида, настраиваемое подчинение и размещение. Поддерживает сценарий «сайд-панель + грид» (основные поля в гриде, детали строки — на панели).
* TMDB\_ST201M / TMDB\_ST201D — таблицы с полями DT и CT типа UN$CM (включает UN$SUMA). Для удобства используются VIEW (VMDB\_ST201M/VMDB\_ST201D), которые разворачивают вложенные типы в набор полей — с ними и работают в SQL.

Абстрактные таблицы

* TMDB\_SALAR\_ABSD1 / ABSD2 — абстрактные таблицы для зарплаты: 9 количеств, 9 сумм, 9 абстрактных параметров, 4 даты. Не подчинены друг другу.
* TMDB\_REG, TMDB\_REG\_A, TMDB\_REG\_A1, TMDB\_REG\_A1D, TMDB\_REG\_A2, TMDB\_REG\_A2D — регистр с большим набором полей (10 сумм, 10 SC, 10 NUM, 10 STR, 5 дат и т.д.). Используются для расширенных задач (в частности — для TMDB\_CMX).

TMDB\_CMX

* Расширённая таблица проводок (CM Extending) — когда стандартного TMDB\_CM не хватает (много полей, нет SPTYPE). PK = NRDOC + COD (здесь нет SPTYPE).
* CODREF — код базовой проводки в том же документе (ссылка только внутри документа).
* Для CMX подготовлен специализированный спецрегистр (TMDB\_REG + детали), чтобы хватало полей.

Справочные данные

* Префикс TMS\_. Справочники — данные, не зависящие от времени (хотя есть периодические справочники).
* Универсальный подход: минимальная общая таблица (TMS\_UNIVERS) + «карточки» для расширения по типам (TMS\_AFX — ОС, TMS\_MPT — материалы/товары, TMS\_MUNC — сотрудники, TMS\_ORG — организации и т. п.).

Справочник TMS\_UNIVERS

* PK: COD.
* Поля: DENUMIREA (название), CODVECHI (старый код для интеграций/импорта), NAMERUS (альтернативное название), UM (единица измерения), TIP (тип — одна буква: F/O/P/ и т. д.), GR1/GR2 (доп. группировки), ISARHIV (архивная пометка вместо удаления), CODI (ссылка на родителя — иерархия), и др.
* TIP/GR1 используются для типизации: например P (продукция), O (организации), R (сотрудники), F (ОС). GR1 часто указывает дополнительный смысл (например, для продукции — номер счета).

Карточки расширения (один-к-одному)

* TMS\_AFX — параметры основного средства (расширение для типа F).
* TMS\_MPT — материалы/товары (расширение для типа P/M).
* TMS\_MUNC — карточка сотрудника (расширение для типа R).
* TMS\_ORG — карточка организации.

Деревья и связи

* TMS\_SYSGRP — связывает элемент UNIVERSe с узлами дерева.
* TMS\_SYSGRPH — описание узлов дерева.
* TMS\_SYSGR — описание самих деревьев.
* Система деревьев позволяет сконфигурировать разные визуальные/функциональные деревья и разделять элементы между ними (один элемент может входить в разные типы деревьев по назначению).

План счетов — TMS\_PDC

* Plan de Contur (план счетов).
* Таблица хранит группы/счета/субсчета (CONT = 0 — группа; CONT > 0 — счёт; CONT1 — субсчёт).
* Вьюшки:
  * VMDB\_PDC — счета.
  * VMDB\_PDCA — субсчета.
  * VMDB\_PDCA1/2, VMDB\_PDCF, VMDB\_PDC\_ADD — дополнительные варианты.
* Поля ATTR1/ATTR2 (обрезанные), TIP/TIP\_1/TIPD и т.п. — определяют, какая аналитика (универс) должна использоваться для данного счета (например SC, DEP, SC1).
* Механизм: при вводе проводки, выпадающий справочник аналитики (Univers) для поля SC строится на основании привязки к счёту — это даёт динамический, контекстный список (на лету).

Справочник TMS\_SYSS (SYSS)

* Используется для множества системных списков (TIP, COD, COD1 — PK).
* Отличие от UNIVERS: SYSS обычно не попадает в проводки; ключ состоит из трёх полей.
* SYSSV — таблица метаданных о разделах SYSS (описывает, какие колонки показывать, заголовки, связи NUMBER1/NUMBER2 и т.д.).
* Поля NUMBER1/NUMBER2 в SYSS часто служат ссылками на другие разделы SYSS (через SYSSV задаётся SCTIP/SCCOD пары для этих полей).
* Вьюшки и правила именования полей: для автоматизации дизайна используют соглашение именования (например FIELD\_R\_2 означает, что поле ссылается на SYSS TIP='R' COD=2). Это позволяет автоматически подставлять справочники в UI без ручной конфигурации.

TMS\_UM — единицы измерения

* Структура: NAME, SHORT\_NAME, ISDEFAULT, BASEID\_SYSS\_UM\_1 (категория измерения).
* Для каждой категории есть базовая единица, остальные имеют коэффициент пересчёта.
* В TMS\_MPT (справочник материалов) есть поля CANT\_ID\_UM и CANT1\_ID\_UM — указывают, в каких единицах хранится количество CANT/CANT1.

Периодические справочники

* Набор TPR\*\_ — описывает прайс-листы: группы, даты и списки цен, связанные с датами.

TSLRPRM\_CALC\* — параметры начисления ЗП

* TSLRPRM\_CALCM (PK = SC\_MUNC, SHTAT\_ID) — параметры на штатную позицию (SHTAT\_ID = 1 — основная должность).
* TSLRPRM\_CALCD (PK = SC\_MUNC, SHTAT\_ID, DATASTART) — периодическая таблица с датами (DATAEND вычисляется триггером).
* Принцип периодичности: на одну кадровую позицию может быть несколько записей с разными DATASTART.

UN9PRODTTREE — регистр норм (BOM / операции)

* Описывает состав изделия (материалы) и операции (трудозатраты), периоды и версии регистров норм.
* Поддержка версии регистров норм, периодов и сложной иерархии материалов/операций.

Системные данные

* UN4SYS\_DATA — таблица настроек Администратора (включая большие CLOB-поля: DOCS, REPORTS, RIGHTS, SETUPS).
  * Записи разделяют настройки по областям; конечный склеенный ini формируется сбором всех записей.
* UN4SYS\_DATA\_ARHIV — триггер копирует изменения из UN4SYS\_DATA в архив (восстановление при ошибках).
* XGRID\_PROP — хранит дизайн интерфейсов/гридов/документов (PK = USERID, OBJID, OBJTYPE, SECTIONNAME). Содержит BLOBVAL с сериализованным дизайном.
  * При переносе узла администратора через XML переносятся и записи XGRID\_PROP (документ + дизайны).
* XLOCKCONTS — таблица контроля доступа к счетам (устаревшая/неиспользуемая).
* X$CHGLOG / X$CHGLOG\_VALUE / XLOG — журналы изменений таблиц (триггеры, которые можно генерировать через P$CHGLOG\_MAKE\_TRIGGER).
* XVERSIONS / XVERS\_DBID — хранение информации об апгрейдах/версиях.

Пакеты (обзор)

* Аббревиатура/название пакета и суть:
  * ABM\_UTIL — утилиты (префикс автора).
  * AFX1 / BG\_AFX / BG\_FORMCONT / BG\_NRSET / BG\_POLICY / BG\_REPORTS — различные модули по ОС и бюджету.
  * PK\_SPELL — представление числа прописью (румынский).
  * SL\_RP — отчёты по зарплате.
  * UN$AVG — расчёт средних цен (долго выполняемые процедуры, запускаются в конце месяца).
  * UN$DBF — импорт DBF в Oracle.
  * UN$G$CMP — нечеткое сравнение строк (функция сходства).
  * UN$GFC — генерация формул проводок (Formule Contabele).
  * UN$G\_PIVOT — построение pivot-таблиц (горизонтальное разворачивание).
  * UN$SOLD / UN$SLD / UN$SLDX — разные реализации расчёта остатков/сальдо (GET\_SOLDT, MAKE, CALC\_SOLD). Реализации отличаются внутренним подходом (временные таблицы vs. XSLD и т.п.). Важно: создание временных таблиц DDL -> блокировки словаря, поэтому избегают повторного создания временных таблиц на лету.
  * UN$DBCLEAR — очистка схемы при подготовке новой компании (create\_tables, fill\_default, clear\_schema).
  * UN$DIV / UN$FM — механизмы фильтрации/политик (InitPolicies/DropPolicies и т. п.).
  * UN$G\_RG1P12 — универсальный отчёт.
  * UN$G$UTIL — утилиты (NNN — Not Null Number, S2N — безопасная конвертация строки→число, TextIncrement, TimeStamp helpers, ContCond/ScCond/ScSpCond/ScGrCont — утилиты формирования SQL-фрагментов по наборам счетов/аналитики).
  * UNP\_INI / UNP\_INI2 — разбор ini-полей Администратора; UNP\_INI2 — новая версия с работой в памяти (быстрее).
  * UN$PLSQL — небольшие вспомогательные PL/SQL процедуры.
  * UN$SCHEMA\_CHECK — проверка схемы на «битые» символы ('????') при копировании/вставке из блокнота.
  * UN$TTEMP — выдача уникальных имён временных таблиц (GetTempName).
  * UN$URX — универсальные отчёты для CMX.
  * UN$USERPARAMS — регистрация пользователя при входе (RegisterUser) и пр.

Процедуры / функции общего назначения

* SAY — форматирует текст для отображения, разбивает строки (ширина по умолчанию 100).
* MSG — выдаёт ошибку через RAISE\_APPLICATION\_ERROR (чтобы показать сообщение пользователю и сделать ROLLBACK).
* WARN — предупреждение (MSG-подобное, но повторный вызов с тем же текстом не будет дублировать).
* GET\_ENV — удобная обёртка для SYS\_CONTEXT('ENVUN4', AName) — получение контекстной переменной.
  * Контекстные переменные — сессийные пары имя/значение. Для безопасной записи в контекст используется пакет ENVUN4 (пакет, которому разрешено писать в контекст), что предотвращает сторонние записи.
  * ENVUN4: EnvSetValue, EnvDropValues (удаление по маске) и т.п.
* SECURE\_CM — наложение политик безопасности на CM (поле/строку) — можно скрывать проводки целиком или обнулять отдельные поля (важно для безопасности и целостности отчётов).
* UN$G$UTIL: ContCond / Cont1Cond / ScCond / ScSpCond / ScGrCont — формирование SQL-фрагментов по пользовательскому набору счетов/аналитики (поддержка синтаксиса с восклицательным знаком — исключение, диапазоны, субсчета в скобках и т. п.).
* CreateSysFIdTable — строит временную таблицу со всеми SysFid из Администратора (полезно для поиска дубликатов SysFid).
* TimeStampInit / TimeStampSay / TimeStampGet — измерение времени выполнения для отладки.

Практические рекомендации и правила

* Работайте с вьюшками, а не напрямую с таблицами (даёт гибкость и возможность менять реализацию без слома вызывающего кода).
* При создании FK:
  * Используйте ON DELETE CASCADE, DEFERRABLE INITIALLY DEFERRED (чтобы проверки выполнялись на COMMIT).
  * На ссылающейся таблице создайте неуникальный индекс по полям FK (предотвратит глобальную блокировку таблицы при Select FOR UPDATE на родителе).
* Для временных таблиц используйте подход с заранее созданными глобальными временными таблицами (ZZTEMP) или централизованную выдачу имён (UN$TTEMP) — избегайте массового DDL в рантайме.
* Для расширений клиента используйте префикс Y<код клиента> для локальных таблиц/пакетов — это облегчает управление и экспорт/импорт.
* Не удаляйте ZZTEMP и системные глобальные таблицы — это может нарушить общие алгоритмы.
* Следите за триггерами, которые генерируют парные проводки (SPTYPE=1) — их сбой вызывает рассинхронизацию сальдо/оборот.

Короткие заметки / тезисы (резюме)

* Таблицы делятся на 3 категории: оперативные (документы/проводки), справочные (универс/карточки) и системные (настройки, логи, дизайны).
* Документ = запись TMDB\_DOCS, проводки = TMDB\_CM / TMDB\_CMX.
* Универсальный справочник TMS\_UNIVERS + карточки (TMS\_\*), SYSS — системные справочники, PDC — план счетов.
* Для сложных документов используют 201M/201D, CST1/2/3, абстрактные регистры (TMDB\_REG/_, TMDB\_CST3_ и пр.).
* Для производительных расчётов остатков реализованы разные пакеты (UN$SOLD, UN$SLD и пр.) с учётом блокировок и временных таблиц.
* Для настроек интерфейса/документов используются UN4SYS\_DATA + XGRID\_PROP (дизайны гридов).
